Arquitectura Hexagonal

Cada microservicio está construido siguiendo la arquitectura hexagonal (también conocida como Ports & Adapters), implementada mediante el scaffold de Clean Architecture de Bancolombia.

Estructura de módulos​

ms-orders/
├── domain/
│   ├── model/          ← Entidades, value objects, gateways (puertos)
│   └── usecase/        ← Casos de uso (lógica de negocio pura)
├── infrastructure/
│   ├── driven-adapters/
│   │   ├── r2dbc-postgresql/    ← Adaptador de base de datos
│   │   └── async-event-bus/     ← Adaptador de Kafka (productor)
│   └── entry-points/
│       ├── reactive-web/        ← API REST (WebFlux)
│       └── async-event-handler/ ← Consumidor de eventos Kafka
└── applications/
    └── app-service/    ← Configuración y bootstrap

Capas y responsabilidades​

Dominio — el núcleo​

Es el corazón de la aplicación. No tiene dependencias externas — solo Java puro. No importa Spring, no importa R2DBC, no importa Kafka.

  • Model — entidades de negocio (Order, OrderItem, Product), value objects (CustomerId, Money, Quantity) y las interfaces de los gateways (puertos)
  • Use cases — implementan la lógica de negocio. Ejemplo: AddItemToOrderUseCase, ReserveStockUseCase

Infraestructura — los adaptadores​

Implementan los puertos definidos en el dominio. El dominio no sabe qué hay aquí.

  • r2dbc-postgresql — implementa OrderRepository usando Spring Data R2DBC
  • async-event-bus — implementa EventsGateway usando Kafka
  • reactive-web — expone los endpoints REST con Spring WebFlux
  • async-event-handler — registra los listeners de eventos Kafka

Principio SOLID predominante​

El principio que más predomina es el Dependency Inversion Principle (DIP):

"Los módulos de alto nivel no deben depender de módulos de bajo nivel. Ambos deben depender de abstracciones."

En la práctica:

// El caso de uso depende de la INTERFAZ (puerto), no de la implementación
@RequiredArgsConstructor
public class AddItemToOrderUseCase {
    private final OrderRepository orderRepo;      // interfaz del dominio
    private final EventsGateway eventsGateway;    // interfaz del dominio
    // No sabe si es PostgreSQL, MongoDB, Kafka o RabbitMQ
}
// La implementación concreta vive en infraestructura
@Repository
public class OrdersReactiveRepositoryAdapter implements OrderRepository {
    // Aquí sí conoce R2DBC y PostgreSQL
}

¿Cómo cambiaría la base de datos?​

Esta es una de las grandes ventajas de la arquitectura hexagonal. Para cambiar de PostgreSQL a MongoDB:

  1. Crear nuevo módulo driven-adapters/mongodb
  2. Implementar las mismas interfaces del dominio
  3. Cambiar la dependencia en app-service/build.gradle

El dominio y los casos de uso no cambian en absoluto. Solo cambia el adaptador.

Flujo de una petición​

Cliente HTTP
      ↓
Handler (reactive-web)        ← entry point
      ↓
Use Case (domain/usecase)     ← lógica de negocio
      ↓
Gateway interface (domain/model) ← puerto
      ↓
Adapter (driven-adapters)     ← implementación
      ↓
PostgreSQL / Kafka

Independencia del framework​

El dominio no importa ninguna clase de Spring. Si mañana cambias de Spring Boot a Quarkus o Micronaut, el dominio no cambia — solo los adaptadores.
