Preguntas frecuentes del panel

Protocolos REST​

¿Qué debemos considerar para actualizar un endpoint sin modificar el anterior?

Versionado de APIs. Se puede implementar de varias formas:

  • En la URL: /api/v1/products y /api/v2/products
  • En headers: Accept: application/vnd.arka.v2+json

En el proyecto actualmente no se implementó versionado, pero la forma recomendada sería por URL ya que es la más explícita y fácil de documentar.

¿Qué comportamiento aplicar cuando estamos autenticados pero no autorizados?

HTTP 403 Forbidden — la diferencia con 401 Unauthorized es:

  • 401 — no estás autenticado (no sabes quién eres)
  • 403 — estás autenticado pero no tienes permisos (sabemos quién eres, pero no puedes)

En el proyecto no se implementó seguridad, pero sería el siguiente paso usando Spring Security con JWT.

¿Qué comportamiento aplicaste cuando no se provee información necesaria?

HTTP 400 Bad Request. Se implementó validación en los constructores de los DTOs:

public record RegisterProductRequestDTO(...) {
    public RegisterProductRequestDTO {
        if (name == null || name.isBlank())
            throw new IllegalArgumentException("name must not be blank");
    }
}

El GlobalExceptionHandler captura la excepción y retorna 400 con el mensaje descriptivo.

Framework — Spring Boot y WebFlux​

¿Qué framework usaste para documentación y qué aporta?

Se intentó implementar Springdoc OpenAPI (springdoc-openapi-starter-webflux-ui). Sin embargo, se encontraron incompatibilidades entre la versión de Spring Boot 4 con WebFlux funcional (RouterFunction) y la versión del plugin.

Como alternativa se documentó la API en esta presentación con ejemplos de requests/responses, diagramas de flujo y descripción de cada endpoint.

En un proyecto real el valor de Swagger/OpenAPI es:

  • Documentación automática sincronizada con el código
  • Interfaz visual para probar endpoints sin Postman
  • Contrato claro entre frontend y backend
  • Generación de clientes automática

¿Por qué usaste programación reactiva?

El scaffold de Bancolombia genera proyectos con Spring WebFlux y R2DBC por defecto, orientado a sistemas de alta concurrencia. En el contexto de ARKA fue relevante porque:

  • No bloqueante — mientras espera respuesta de la DB, el hilo puede atender otras peticiones
  • Backpressure — control de flujo cuando hay muchas peticiones simultáneas
  • Composición — encadenar operaciones asíncronas de forma declarativa con flatMap, map, thenReturn

El mayor reto fue el cambio de mentalidad de imperativo a reactivo — especialmente manejar errores y encadenar operaciones que dependen del resultado de la anterior.

Pruebas Unitarias​

¿Aplicaste pruebas unitarias?

Honestidad sobre el estado

Las pruebas unitarias no fueron implementadas en este proyecto. Fue una decisión consciente de priorizar la funcionalidad dada la complejidad del sistema (3 microservicios, Kafka, AWS), pero reconozco que es una deuda técnica importante.

¿Cómo se deberían implementar?

Para los casos de uso con JUnit y Mockito:

@ExtendWith(MockitoExtension.class)
class AddItemToOrderUseCaseTest {

    @Mock
    private OrderRepository orderRepo;

    @Mock
    private OrderItemRepository orderItemRepo;

    @Mock
    private EventsGateway eventsGateway;

    @InjectMocks
    private AddItemToOrderUseCase useCase;

    @Test
    void shouldAddItemToExistingDraftOrder() {
        // Given
        Order existingOrder = Order.createDraft(new CustomerId(1));
        AddItemToOrderCommand command = new AddItemToOrderCommand(1, 1, 2, new BigDecimal("50000"));

        when(orderRepo.findDraftOrdersByCustomerIdAndStatus(1, "DRAFT"))
                .thenReturn(Mono.just(existingOrder));
        when(orderItemRepo.saveItem(any(), any()))
                .thenReturn(Mono.just(new OrderItem(...)));
        when(eventsGateway.emit(any(), any()))
                .thenReturn(Mono.empty());

        // When
        StepVerifier.create(useCase.addItemToOrder(command))
                // Then
                .expectNextMatches(result -> result.orderId() != null)
                .verifyComplete();
    }
}

¿Cómo probar una funcionalidad tipo Void?

Con StepVerifier de Reactor:

@Test
void shouldEmitEventWhenItemAdded() {
    // ...mocks...
    
    StepVerifier.create(useCase.addItemToOrder(command))
            .verifyComplete(); // verifica que completa sin error
    
    verify(eventsGateway).emit(eq(StockReserveRequestedEvent.TOPIC), any());
}

¿Qué principio tuviste en mente al diseñar pruebas?

El principio AAA (Arrange, Act, Assert):

  • Arrange — preparar los mocks y datos de entrada
  • Act — ejecutar el método bajo prueba
  • Assert — verificar el resultado esperado

Y el principio de una sola responsabilidad por prueba — cada test verifica exactamente una cosa.

Bases de Datos​

¿Qué ofrecerías sin JPA y qué implicaciones tiene?

Exactamente lo que implementé — R2DBC (Reactive Relational Database Connectivity). Las implicaciones son:

JPAR2DBC
Bloquea el hiloNo bloquea (reactivo)
Relaciones automáticasRelaciones manuales
Cascade automáticoCada operación es explícita
Lazy loadingNo existe
@OneToManyfindByOrderId() manual

Por ejemplo, para guardar una orden con items en JPA bastaba con save(order) y el cascade hacía el resto. Con R2DBC hay que hacerlo explícitamente:

return orderRepository.save(orderData)
        .flatMap(savedOrder -> {
            List<OrderItemData> items = mapper.toItemsData(order, savedOrder.getId());
            return orderItemRepository.saveAll(items)
                    .collectList()
                    .thenReturn(savedOrder);
        });

¿Manejaste transacciones?

No se implementaron transacciones explícitas con @Transactional. En R2DBC se pueden usar con @Transactional de Spring, pero en programación reactiva requiere configuración adicional con TransactionalOperator. Es una mejora pendiente — actualmente si falla el guardado de los items después de guardar la orden, quedarían datos inconsistentes.

Buenas Prácticas​

¿Qué principios aplicaste para código limpio?

  • SOLID — Single Responsibility — cada clase tiene una sola razón para cambiar. AddItemToOrderUseCase solo maneja agregar items, ReserveStockUseCase solo reserva stock.
  • SOLID — Dependency Inversion — los casos de uso dependen de interfaces (gateways), no de implementaciones concretas.
  • DRY (Don't Repeat Yourself) — el mapper centraliza la transformación entre capas.
  • KISS (Keep It Simple) — métodos cortos y con nombres descriptivos.

¿Cómo manejaste las excepciones?

Con un GlobalExceptionHandler centralizado que mapea cada tipo de excepción a su código HTTP correspondiente:

@ExceptionHandler(ProductNotFoundException.class)
→ 404 NOT_FOUND

@ExceptionHandler(BusinessRuleException.class)  
→ 422 UNPROCESSABLE_ENTITY

@ExceptionHandler(IllegalArgumentException.class)
→ 400 BAD_REQUEST

@ExceptionHandler(Exception.class)
→ 500 INTERNAL_SERVER_ERROR

¿Usaste algún patrón de diseño?

  • Repository Pattern — abstrae el acceso a datos detrás de interfaces
  • Gateway Pattern — abstrae la comunicación con sistemas externos (Kafka, SES)
  • Adapter Pattern — implementaciones de infraestructura que adaptan los puertos del dominio
  • Factory Method — Order.createDraft(), StockMovement.createReserved() para construcción controlada de objetos

Arquitectura Hexagonal y DDD​

¿Qué habría que hacer para cambiar de motor de base de datos?

Solo cambiar el adaptador en driven-adapters/r2dbc-postgresql. El dominio y los casos de uso no cambian en absoluto — solo la implementación del repositorio. Por ejemplo, para cambiar a MongoDB:

  1. Crear nuevo módulo driven-adapters/r2dbc-mongodb
  2. Implementar las mismas interfaces del dominio (OrderRepository, ProductRepository)
  3. Cambiar la dependencia en app-service/build.gradle

El dominio no sabe ni le importa qué base de datos hay detrás.

¿Qué principio SOLID predomina en arquitectura hexagonal?

Dependency Inversion Principle (DIP) — los módulos de alto nivel (casos de uso) no dependen de módulos de bajo nivel (base de datos, Kafka). Ambos dependen de abstracciones (interfaces/gateways).

SDLC / CI-CD​

¿Qué tecnologías implementaste?

  • Docker + Docker Compose — contenedorización de todos los servicios
  • GitHub Actions — pipeline de CI/CD para deploy automático de esta documentación
  • LocalStack — simulación de AWS en local
  • CloudFormation — infraestructura como código

¿Buenas prácticas para sincronizar un equipo?

  • Git Flow — ramas por feature, pull requests para revisión
  • Conventional Commits — mensajes de commit estandarizados (feat:, fix:, docs:)
  • Variables de entorno — nunca credenciales en el código, siempre en .env
  • Docker Compose — cualquier desarrollador levanta el ambiente completo con un comando

¿Qué escalabilidad implementaste?

  • Microservicios independientes — cada servicio escala por separado
  • Kafka con particiones — los tópicos tienen 3 particiones para procesamiento paralelo
  • Programación reactiva — manejo eficiente de concurrencia sin bloquear hilos

Cloud — AWS​

¿Cómo desplegaste en AWS?

Se usó LocalStack para simular AWS en local. Los servicios utilizados:

ServicioUso
Secrets ManagerCredenciales de DB y Kafka
S3Almacenamiento de reportes CSV
SQSCola para reportes programados
EventBridgeReglas de eventos periódicos
SESEnvío de correos (preparado)

La infraestructura está definida en CloudFormation (infra.yaml) y se despliega automáticamente al iniciar LocalStack.

¿Cómo monitorizarías logs y métricas en AWS real?

  • CloudWatch Logs — los contenedores enviarían logs usando el driver awslogs
  • CloudWatch Metrics — métricas de CPU, memoria y custom metrics con Micrometer
  • Spring Actuator — ya configurado con endpoints /actuator/health y /actuator/prometheus
  • X-Ray — distributed tracing para seguir una request a través de los microservicios

¿Variable de acceso?

En LocalStack se usan credenciales ficticias:

AWS_ACCESS_KEY_ID=test AWS_SECRET_ACCESS_KEY=test

En producción se usarían IAM Roles para los servicios en ECS/EKS, evitando credenciales hardcodeadas. Para desarrollo local, variables de entorno en .env nunca commiteadas al repositorio.
